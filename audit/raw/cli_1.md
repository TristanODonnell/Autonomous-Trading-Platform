### src/autonomous_trading_platform/cli/commands/backtesting.py (3645 lines — largest file in this batch)
- Purpose: Legacy/umbrella CLI for backtest fixture seeding and "is this feature actually wired?" verification harnesses (risk parameters, notification events, governance/allocation, auto-promotion, auto-demotion). The entire module is registered under `atp backtesting ...` and every subcommand's `--help` text is prefixed `[DEPRECATED] Use: atp <canonical-domain-command>` — but it is not a dead file: several "canonical" command modules audited above (`controls.py`, `operations.py`, `platform.py`, `governance.py`) `import` and directly call this module's handlers rather than reimplementing the logic.
- Commands exposed (14, under `backtesting`): `run`, `inspect-results`, `seed-fixture`, `seed-settings`, `read-settings`, `seed-controls`, `read-controls`, `read-portfolio`, `read-dashboard`, `verify-risk-parameter-effects`, `verify-notification-events`, `verify-governance-allocation`, `verify-auto-promotion`, `verify-auto-demotion`.
- Notable:
  - **Deprecation direction is backwards.** `atp platform fixture seed` / `atp platform dashboard-snapshot` (`platform.py`) are pure forwards into `handle_seed_fixture`/`handle_read_dashboard` here; `atp operations verify-notification-events` forwards into `handle_verify_notification_events`; `atp governance verify-auto-promotion`/`verify-auto-demotion`/`verify-allocation(-source-of-truth)` forward into `handle_verify_auto_promotion`/`handle_verify_auto_demotion`/`handle_verify_governance_allocation`. So the module telling users it's deprecated in favor of the canonical domains is actually the one holding the real implementation for 5+ of those "canonical" commands — a genuine layering/naming inversion, not just cosmetic duplication.
  - `handle_run`/`handle_inspect_results` are literal stubs returning `{"status": "not_implemented"}` — dead commands left registered and discoverable via `--help`.
  - `handle_seed_fixture` (238-411) hand-rolls a full multi-table write transaction (strategy_configs, strategy_governance, strategy_control_states, allocation_overrides, operator_settings, runtime_control_state) directly against repositories/raw ORM `setattr` from the CLI handler — business-orchestration logic in `interfaces/`, not `application/`. `handle_seed_controls` (513-676) and the internal helper `_verify_seed_state` (1033-1157) each independently re-implement most of this same multi-table seed/delete-and-reseed sequence — three near-duplicate persistence pipelines for "write a strategy+governance+controls+allocation fixture" in one file.
  - The five `verify-*` commands are not read-only diagnostics despite living alongside genuinely read-only "read-*" commands in the same file — they seed synthetic rows into the real configured DB, invoke actual services/replay runners (`RuntimeReplayDebugRunner`, `AutoPromotionService`, `AutoDemotionService`, `QualityBasedReallocationService`, `StrategyGovernanceService`), assert expected outcomes, print PASS/FAIL tables, write JSON artifacts under `artifacts/backtesting/`, and return **exit code 1 on any failed assertion** (`handle_verify_auto_promotion`/`handle_verify_auto_demotion`: `return 0 if all(row["status"] == "PASSED" ...) else 1`). This is pytest-shaped integration-test logic implemented as a CLI command instead of as a test in `tests/`, and it is the single largest concentration of business/verification logic anywhere in the `cli/commands` package — roughly 2,400 of the file's 3,645 lines (893-3307) are these five verify commands plus their seed/evidence/classification helpers.
  - `handle_verify_notification_events` calls the real `RuntimeControlService.activate_kill_switch(...)` then `release_kill_switch(...)` against the live configured database as part of "verification" — a side effect (real KILL_SWITCH_ACTIVATED audit rows, a moment where trading is actually halted) baked into what reads as a diagnostic/verify command name.
  - `_auto_promotion_audit_seed`, `_auto_demotion_audit_seed`, and `_governance_audit_transition_probes` (2627-3485, ~850 lines combined) are hand-built ORM fixture factories — constructing `StrategyConfigs`/`StrategyGovernance`/`SimulationRuns`/`MetricsSummary`/`DatasetVersions`/`CashSnapshot` rows inline with hardcoded 2026-01-01 dates and UUID-suffixed synthetic strategy IDs — this is textbook test-fixture-factory code (cf. `tests/factories`, `tests/utilities`) living in production `src/`, not test code.
  - `_GOVERNANCE_SETTING_WIRING` (1889-1963) and `_governance_audit_settings_field_classification` (2971-3053) are static, hand-maintained tables asserting which `operator_settings` fields are `WIRED` / `FLAG_NOT_WIRED` / `DEPRECATED_PERSISTED_ONLY` / `RISK_BLOCKING_ONLY` etc., each with a free-text explanatory `note`. Nothing ties these classifications to the actual services at runtime — only the PASS/FAIL probes are behaviorally checked; the wiring-status narrative itself is unverified documentation-as-code with real drift risk if a service is later wired up without updating this table.
  - `_verify_determine_status` (1179-1317) hand-codes parameter-specific effect classification (`WIRED_AND_EFFECTIVE`, `PERSISTED_ONLY_NOT_WIRED`, `STUBBED_OR_DEFERRED`, `WIRED_BUT_NO_EFFECT_IN_THIS_SCENARIO`) via if/elif branches keyed on `param_name` string literals — a maintenance hazard if `_VERIFY_PARAM_CONFIGS`'s keys and this function's branches drift apart (no shared enum/schema enforces they stay in sync).

## Standout candidates
- `backtesting.py` `handle_verify_auto_promotion`/`handle_verify_auto_demotion`/`handle_verify_governance_allocation`/`handle_verify_notification_events`/`handle_verify_risk_parameter_effects` — ~2,400 lines of pytest-shaped integration-test/assertion logic (seed DB → run real services → assert → exit code 1 on failure) implemented as CLI commands rather than as tests; single largest concentration of misplaced business/verification logic in the package, and the module telling operators it's "[DEPRECATED]" is the one other "canonical" modules actually depend on for their implementation.
- `admin.py` `handle_doctor` — ~80 literal duplicated lines (copy-pasted `handle_validate_config` + `handle_inspect_db` bodies) instead of calling them.
- `governance.py` — largest "legitimate" file (1703 lines) but genuinely disciplined thin-wrapper pattern at scale; `_STATE_ALIASES` is an explicitly-commented, acknowledged-but-unreconciled duplication of `StrategyGovernanceService._STATE_ALIASES`.
- `portfolio.py` `_allocation_payload`/`_reconciliation_payload` — real source-of-truth fallback policy and a second, CLI-only reimplementation of "holdings + cash == summary" invariant checking.
- Cross-file symbol-parsing duplication: `_parse_symbols`/`_SYMBOL_RE` appears independently in `features.py` and `ingestion.py` (near-identical regex/dedup logic).
