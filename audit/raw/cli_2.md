## Non-commands files (framework/app wiring)

### src/autonomous_trading_platform/cli/__init__.py (0 lines)
- Purpose: Empty package marker, no content.
- Notable: Nothing to note — truly empty.

### src/autonomous_trading_platform/cli/main.py (63 lines)
- Purpose: Entry point. Builds an `argparse.ArgumentParser` with `prog="atp"`, registers all 18 command-domain modules (safety, diagnostics, ingestion, strategy, execution, runtime, controls, backtesting, admin, operations, portfolio, universe, features, research, settings, risk, governance, platform) as subparsers, then dispatches to `args.func` via `run_handler`.
- Commands exposed: N/A (top-level wiring only, no leaf commands itself).
- Notable: Clean, minimal composition root. No business logic. If `args.func` is missing (i.e., user didn't pick a leaf subcommand), prints help and returns 1 rather than crashing. Confirms the CLI is a flat `argparse` tree (`atp <domain> <subcommand> [flags]`), not click/typer — a somewhat old-school but perfectly serviceable choice for an internal ops CLI.

### src/autonomous_trading_platform/cli/runner.py (17 lines)
- Purpose: Single `run_handler(handler, args) -> int` wrapper: calls the dispatched handler function, and on any `Exception` prints an `[ERROR]` line plus a full traceback via `format_exception`, returning exit code 1 instead of letting the process crash with a raw stack trace.
- Notable: This is the *only* top-level exception boundary for the entire CLI — every one of the 150+ leaf commands' uncaught exceptions funnel through here. Simple and correct. Slight smell: it catches bare `Exception`, so a command handler's own more specific error handling (e.g., DB-not-ready detection in strategy.py) has to happen inside the handler itself, and this outer layer can't distinguish user error from bug — everything looks the same (exit code 1, traceback dumped to stdout, not stderr).

### src/autonomous_trading_platform/cli/formatters.py (30 lines)
- Purpose: Five tiny print helpers — `print_header`, `print_kv_rows`, `print_success`, `print_error`, `print_json` (JSON with `indent=2, default=str`) — plus `format_exception` for traceback string formatting.
- Notable: All output goes to stdout via plain `print()`, including `print_error` (prefixed `[ERROR]`) — no stderr usage anywhere in the CLI's output layer, which would matter if any caller tried to pipe/parse stdout while filtering errors. `default=str` on `print_json` is a pragmatic catch-all for Decimal/datetime/enum serialization without custom JSON encoders — reasonable but silently stringifies anything unexpected (no whitelist of expected types), so a bug that returns an unexpected object type won't surface as a serialization error, just an oddly-stringified field.

### src/autonomous_trading_platform/cli/helpers.py (25 lines)
- Purpose: Single function `parse_datetime(value: str) -> datetime` — accepts ISO8601 with/without trailing `Z`, or bare date, normalizes everything to UTC-aware `datetime`.
- Notable: Reused across research.py, universe.py, runtime.py, runtime_soak_loop.py, risk.py, strategy.py, settings.py for all `--timestamp`/`--start`/`--end`-style flags — genuinely shared, non-duplicated utility. Wraps all parse failures in a `ValueError` with a clear message. Good, minimal, no smells.

**Framework characterization:** the 5 non-command files total only 135 LOC combined. There is no DI container, no shared "CliContext" object, no output-format abstraction beyond raw `print`/`print_json`, and no shared session-lifecycle helper (each command handler calls `get_session()` and manages `session.close()`/`session.commit()` itself, inconsistently — see below). This is about as thin as CLI scaffolding gets: an argparse tree + one error boundary + two tiny formatting/parsing utility modules. All the actual weight (9,594 of 9,729 LOC, 98.6%) lives in the 8 domain command files.

### src/autonomous_trading_platform/cli/commands/strategy.py (671 lines, 12 commands)
- Purpose: Strategy catalog / registry inspection CLI — list/inspect strategy types and components from in-memory registries (no DB), plus list/inspect/compare persisted strategies and equity curves from the DB via `StrategyCatalogService`/`ActiveStrategiesService`.
- Commands exposed: `evaluate-bar` (deprecated, forwards to `runtime evaluate-cycle`), `inspect-readiness` (marked "[DOMAIN-MISALIGNED]" in its own help text), `list-types`, `inspect-type`, `validate-config`, `list`, `inspect`, `compare`, `equity-curve`, `list-components`, `inspect-component`, `active`.
- Notable:
  - **Self-documented layering smells**: two commands' `help=` strings literally say `[DEPRECATED]` and `[DOMAIN-MISALIGNED]` and explain the command should live elsewhere ("should be moved to 'operations inspect-ingestion-readiness' or 'diagnostics ingestion-readiness'"). Rare to see a codebase admit architectural drift directly in user-facing `--help` text rather than silently carrying the smell.
  - `handle_evaluate_bar` does a same-package cross-import (`from autonomous_trading_platform.cli.commands import runtime as _runtime`) and just calls `_runtime.handle_evaluate_cycle(args)` — a forwarding shim kept only for CLI backward compatibility.
  - Thin-wrapper pattern is consistent here: DB-backed commands build a small local `StrategyCatalogDependencies` dataclass, instantiate `StrategyCatalogService`/`ActiveStrategiesService` with the session, and call one service method, then `print_json` the result — no business logic duplicated in the CLI layer for the DB-backed paths.
  - Registry-backed commands (`list-types`, `inspect-type`, `list-components`, `inspect-component`) do real work in the CLI file itself — `_strategy_definition_to_dict`, `_component_definition_to_dict`, `_parameter_spec_to_dict` are ad hoc serializers that reach into internal registry object attributes (e.g. `defn.compute_warmup_bars()`, `defn.export_parameter_schema()`) and manually flatten ~15-20 fields each. This is presentation logic (arguably fine for a CLI) but it duplicates shape-definition responsibility that in a Pydantic-contracts-first codebase (per CLAUDE.md) would normally live in `contracts/`. No contract model is used for these outputs — dicts are hand-assembled.
  - Repeated `_db_not_ready` / `_is_missing_table` exception-classification boilerplate appears identically in `handle_list`, `handle_inspect`, `handle_compare`, `handle_equity_curve`, `handle_active` (5x near-identical `try/except (OperationalError, ProgrammingError)` blocks) — could be a decorator or context manager but isn't.
  - `validate-config` has real, non-trivial UX care: mutually exclusive `--parameters` (inline JSON) vs `--parameters-file`, with a PowerShell-specific epilog example (`RawDescriptionHelpFormatter`) documenting escaped-quote pitfalls — a thoughtful touch given the dev environment is Windows.

### src/autonomous_trading_platform/cli/commands/safety.py (704 lines, 13 commands)
- Purpose: Kill-switch / live-trading-gate CLI — status inspection, emergency halt, arm/disarm, pre-trade local gate check, safety-scoped audit log.
- Commands exposed: `status`, `kill-switch-status`, `emergency-halt`, `release-kill-switch`, `assert-gate`, `audit-log`, `startup-check`, `pre-trade-check`, `arm-live`, `disarm-live`, `enable-kill-switch`, `disable-kill-switch`, `gate-status`.
- Notable:
  - Consistent `SafetyDependencies` dataclass + `build_dependencies()` factory pattern — every handler follows `deps = build_dependencies(); try: ...; finally: deps.session.close()`.   - `_gate_status_payload` aggregates 4 independent boolean checks (environment/account/runtime/kill-switch) with individually caught exceptions appended to an `errors` list — reasonable non-fail-fast status aggregation, thin orchestration only (all real logic lives in the safety services).

  - `_summarize_config_dicts` builds throwaway `type("_ConfigView", (), item)()` dynamic classes purely to satisfy `_component_usage`/`_template_usage`'s expectation of an object with a `.parameters` attribute, when both helper functions could just as easily accept dicts — an odd, slightly obscure workaround (dynamic class-from-dict) for what's a simple duck-typing mismatch.
  - `handle_resume_experiment` is a genuine **safety-oriented deprecation guard**, not just a compat shim: it rejects `--execute` outright with `SystemExit` and a message explaining execution must happen inside research pipeline stages "so live/paper runtime orchestration is untouched" — deliberately preventing the CLI from becoming an accidental live-execution trigger for a resume path that should only run within guarded pipeline code.
  - Every command in this file supports `--format json|yaml|table` via the shared `_print_payload` helper (table format falls back to a flat key:value dump, not a real tabular renderer) — more consistent output-format handling than any other file in scope, though "table" is really just "flat text," reusing the same non-abstraction noted in runtime.py's manual `print(f"  {k:<28} {v}")` pattern rather than something built on `formatters.print_kv_rows`.
  - Two DB session context-manager styles coexist in the same file: most handlers use manual `session = get_session(); try/finally: session.close()`, but `handle_black_litterman_run` uses `with get_session() as session:` — implies `get_session()` supports being used as a context manager, but only one handler in the entire 13-file scope actually uses it that way; a real, if minor, inconsistency in how the shared `db.get_session()` helper is consumed across handlers.

### src/autonomous_trading_platform/cli/commands/universe.py (2151 lines, 36 commands — largest command file in scope by leaf-command count)
- Purpose: Full universe-management CLI — raw market pool refresh/inspection, candidate generation and rejection inspection, universe version CRUD (seed/inspect/validate/export/import), propose-rebalance/rotate/rollback governance workflow, rotation/rebalance audit history, and cross-cutting inspection (runtime-status, observability-status, replay-timeline, symbol-history, lifecycle-symbol, compare-universes).
- Commands exposed (36): `select-now`, `inspect-active`, `inspect-symbols`, `inspect-symbol`, `inspect-version`, `validate-active`, `validate-version`, `validation-report`, `inspect-ingestion-input`, `seed`, `raw-pool-refresh`, `raw-pool-inspect`, `raw-pool-history`, `raw-pool-inspect-symbol`, `candidate-generate`, `candidate-inspect`, `candidate-inspect-rejections`, `candidate-inspect-symbol`, `history`, `export-version`, `import-version`, `runtime-status`, `observability-status`, `propose-rebalance`, `rotate`, `rollback`, `rotation-history`, `inspect-rotation`, `rebalance-history`, `inspect-rebalance`, `rotation-status`, `history-for-date`, `replay-timeline`, `compare-universes`, `symbol-history`, `lifecycle-symbol`.
- Notable:
  - Same `UniverseDependencies` dataclass + `build_dependencies()` factory pattern as `safety.py` — consistent `deps = build_dependencies(); try: ...; finally: deps.session.close()` session lifecycle for the ~20 handlers that need the full service bundle. However roughly half the handlers (`raw_pool_*`, `history`, `rotation_*`, `rebalance_*`, `symbol_history`, `lifecycle_symbol`) bypass `build_dependencies()` entirely and call bare `get_session()` + construct one-off repositories inline instead — the same "two competing session-acquisition styles in one file" pattern seen elsewhere in this scope (research.py), just localized within a single file rather than across files.
  - Extremely thin wrapper discipline for the governance-critical mutation commands: `seed`→`UniverseVersionService.build_version`/`validate_version_row`, `select-now`→`run_universe_selection_cycle()`, `raw-pool-refresh`→`run_raw_market_pool_refresh()`, `candidate-generate`→`run_candidate_generation()`, `propose-rebalance`→`run_rebalance()`, `rotate`→`run_universe_rotation()`, `rollback`→`run_universe_rollback()` — every one of the "real" universe-mutating operations is a single call into a `universe/jobs/run_*` function; the CLI handler's own logic is limited to timestamp resolution, dry-run branching, and payload shaping. No governance/selection/rotation business logic is reimplemented in the CLI layer — the cleanest thin-wrapper file in the whole 13-file scope by that measure, likely because universe rotation is safety/governance-sensitive and the design deliberately keeps all decision logic in `universe/jobs/` and `universe/services/`.
  - Operator-identity nudging pattern repeated 3x (`seed`, `candidate-generate`, `import-version`): each success payload includes an `"operator_identity_warning"` field that's non-null (a reminder string) only when `--approved-by` was omitted and the action wasn't a dry-run — a soft nudge toward attribution on manual universe mutations without hard-enforcing it (`--approved-by` is optional, not `required=True`, unlike e.g. safety.py's `--confirm-release`). Inconsistent strictness compared to safety.py where destructive actions require explicit confirmation flags.
  - `handle_validation_report` is a one-line pure alias: `return handle_validate_active(args)` — yet another instance of the "duplicate command name forwards to another handler" pattern seen repeatedly in this scope (strategy.py's `evaluate-bar`, safety.py's `enable/disable-kill-switch`), here without even an explanatory docstring/comment for why both names exist.
  - `handle_compare_universes` computes churn_pct with `max(len(syms_a | syms_b), 1)` guarding divide-by-zero — a small correctness nicety, and its payload conditionally includes full `only_in_a`/`only_in_b` symbol lists only when `--output` is set (keeping stdout JSON compact while still writing complete data to file) — a deliberate two-tier output-size design not seen elsewhere in scope.
  - Several handlers do lazy same-scope re-imports of already-module-level-imported names — e.g. `handle_history` imports `select` from `sqlalchemy` locally even though nothing else in the module needs it at import time, and `handle_observability_status` imports `Path` locally despite `Path` already being imported at module level (line 8) — a redundant duplicate import inside one function, harmless but sloppy.
  - `_rebalance_payload`/`_rotation_payload`/`_version_payload`/`_member_payload` (~90 lines total) are hand-built dict-mapper functions in the same style as every other file in this scope (risk.py, safety.py, runtime.py) — no shared "SQLAlchemy row → dict" helper exists anywhere in the CLI layer; each file reinvents this per-model, another cross-file duplication candidate (though the field sets are all domain-specific enough that a generic helper would need per-model column lists anyway, limiting how much real duplication this represents).
  - Command surface size (36 leaf commands, the largest in the whole 13-file scope) reflects universe management's genuine operational complexity (raw pool → candidates → rebalance proposals → rotation → rollback, each independently inspectable) rather than obvious redundancy — unlike research.py's stub-heavy tail, nearly every universe.py command here maps to a real, distinct read or governed-write operation against a real service/job.

## Gaps/smells
- No shared DB-session lifecycle helper across the CLI as a whole: three distinct patterns coexist — (1) per-file `XDependencies` dataclass + `build_dependencies()` factory (safety.py, universe.py — cleanest/most consistent), (2) ad hoc `session = get_session(); try/finally: session.close()` repeated per-handler with no shared factory (risk.py, runtime.py, settings.py, most of research.py and universe.py), (3) a single one-off usage of `with get_session() as session:` context-manager style (research.py's `handle_black_litterman_run` only, nowhere else in 151 commands). No enforcement that a given file — let alone the whole CLI — picks one style.
- `_db_not_ready`/`_is_missing_table` exception-classification pattern duplicated 5x within strategy.py alone — no shared decorator (confirmed still true after full read; no analogous pattern needed elsewhere since most other files' read paths don't special-case missing-table errors).
- `_jsonable`/`_write_payload` (Decimal/datetime-safe JSON+YAML serialization helpers) are duplicated byte-for-byte across settings.py and risk.py (and research.py/universe.py have their own separate near-equivalents: `_write_artifact`/`_load_artifact` in research.py, `_write_json_output`/`_emit_payload` in universe.py) — five files independently reinvent "serialize a payload dict to JSON or YAML, handling Decimal/datetime," none sharing from `cli/formatters.py` or a common module.
- The "assemble a synthetic `OrderIntent` + stub readers to run a local pre-trade safety check without touching the broker" pattern is implemented **twice**, independently, in `safety.py`'s `handle_pre_trade_check` and `risk.py`'s `handle_pretrade_check` — different field sets, different idempotency-key/client-order-id formats, same underlying intent. The clearest case of duplicated near-business-logic (not just formatting) across files in the full scope.
- Cross-file private-function imports: `runtime_soak_loop.py` imports `research.py`'s underscore-prefixed `_load_experiment_from_yaml` directly; `risk.py`'s `_drawdown_config_payload` reaches into `DrawdownGovernanceService`'s private `_load_config()` method — both are mild encapsulation leaks from the CLI layer into "private" internals of other modules.
- Two hand-maintained parallel registries in runtime.py (`_DISPATCHERS` dict and `_job_side_effects_note()`'s notes dict) must independently track which of the 20+ `SCHEDULER_REGISTRY` jobs are CLI-dispatchable and what their side effects are — no compile-time or test-enforced sync with the actual job registry, so registry drift (a new job added without updating both dicts) fails silently as `cli_dispatchable: false` rather than erroring.
- research.py contains ~6 commands whose action-verb names promise computation they don't perform (`analyze-regimes`, `intelligence rank-candidates/cluster-strategies/predict-robustness`, `run-validation`, `calibrate-slippage` all just validate an input and emit a `"status": "planned"` artifact) — a naming/expectations gap rather than a code-quality issue, but real enough that a CLI user following `--help` text alone would be misled about what actually runs.
- settings.py's `handle_advanced` returns a **hardcoded stub cost model** (`fixed_commission=0`, `slippage_rate=0.0001`, comment "simulation defaults") as if it were live configuration data rather than reading any real settings table — dormant fabricated data presented through a real CLI command.
- All CLI error/success output goes to stdout (including `print_error`), never stderr — no separation for piping (confirmed true across every file read; `runtime.py`'s non-JSON human-readable mode is the only file offering an output-mode alternative, and it also writes to stdout only).
- Confirmation-flag strictness is inconsistent across mutation commands: safety.py requires `--confirm-release` (`required=True`, hard block) for kill-switch release/disable, while universe.py's `seed`/`candidate-generate`/`import-version` only soft-nudge via an `operator_identity_warning` string in the output payload when `--approved-by` is omitted — no hard requirement. Both are "governance-sensitive" mutation paths but enforce operator attribution at different strictness levels.
