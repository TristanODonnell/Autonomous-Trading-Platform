## ORM-usage claim (verified across scope)

CLAUDE.md claims "Repositories follow UnitOfWork pattern; never call ORM directly from services." **This is violated in this scope.** Direct `session.scalars(select(...))` / `session.query(...)` / `session.add(...)` / `session.commit()` calls on ORM models exist in:
- `metric_lineage_service.py` (lines 414–423: `session.scalars(select(MetricsSummary)...)`)
- `operational_alert_service.py` (builds `select(OperationalAlert)`, `session.add`, six `session.commit()` calls)
- `platform_backtest_service.py` (`session.query(_SRS).update(...)`, many `session.commit()/flush()`)
- `portfolio_analytics_service.py` (numerous `select(CashSnapshot/PositionSnapshot/...)` + `session.scalars`)
- `quality_based_reallocation_service.py` (`session.execute`, `session.scalars`, flush/commit)
- `platform_replay/research_hooks.py` (`session.query(DatasetVersions)`, `session.add`, `session.flush`)
- `platform_replay/settings_hooks.py`, `platform_replay/universe_hooks.py`, `platform_replay/risk_hooks.py` (commit/flush)
- `runtime_control_service.py`, `runtime_snapshot_service.py` (indirect, via other services) (`select(StrategyGovernance)`/`select(StrategyControlState)` direct)
- `strategy_allocation_service.py` (extensive: `select(StrategyGovernance)`, `select(StrategyControlState)`, `session.get(StrategyConfigs, ...)`)
- `strategy_catalog_service.py` (pervasive: `select(StrategyConfigs)`, `select(StrategyGovernance)`, `select(MetricsSummary).join(SimulationRuns)`, `select(AuditLogRow)`, `select(Experiments)`, `session.add(...)` — no repository layer at all in this file)
- `strategy_control_service.py`, `strategy_governance_service.py`, `strategy_health_lifecycle_service.py`, `strategy_health_monitor.py` (all do `select(StrategyGovernance)` directly for latest-governance/monitorable-strategy lookups, alongside otherwise repo-backed writes)
- `system_health_service.py` (`self._session.query(StrategyGovernance).filter(...).count()` — legacy `Session.query()` style, not even `select()`)

**Correction**: an earlier pass in this file listed `system_health_service.py` as repository-only. On full read, that is wrong — see per-file entry below. The only files in this scope that are genuinely clean (no direct ORM statement construction anywhere) are `operations_service.py`, `operator_settings_service.py` (repo-only; ORM row models imported only as type references), `recent_activity_service.py`, `portfolio_summary_service.py`, `portfolio_equity_curve_service.py`, `portfolio_construction_pipeline.py`, `optimization_backend.py`, `simulation_vs_paper_comparison_service.py` (pure computation, no session at all), `runtime_soak_verification_service.py` (re-export shim).

### src/autonomous_trading_platform/application/services/quality_based_reallocation_service.py (1246 lines)
- Purpose: `QualityBasedReallocationService.rebalance()` computes and (idempotently, concurrency-safely) writes quality-weighted capital allocation overrides across active strategies, blending backtest and live-performance quality scores and respecting manual overrides, per-strategy caps, and a minimum-change hysteresis threshold.
- **VERIFIED — matches claimed behavior on idempotency/locking**: uses a rebalance_run_id-keyed idempotency guard (`_record_retry_detected` short-circuits if a prior run with that ID already reached a terminal status), a PostgreSQL transaction-scoped advisory lock (`pg_try_advisory_xact_lock`, auto-releases on commit/rollback) plus a row-based "active running" guard as defense-in-depth for SQLite/test environments where advisory locks aren't available, and a configurable minimum-rebalance-interval guard. All guard paths (`disabled`, `interval`, `concurrent`, `retry`) write an `AllocationRebalanceHistory` row and an audit-log entry, so every invocation — even a no-op skip — is traceable.
- Notable: **Confirmed duplicate scoring formula** — `_quality_score`/`_live_quality_score` here use the identical weight constants (Sharpe 0.40, return 1.50, win-rate 0.40, trade-count scale 100/cap 0.25, drawdown penalty 2.00, floor 0.01) as `metric_lineage_service.py`'s module-level `_research_quality_score`/`_live_quality_score`, just written out inline with `Decimal` arithmetic instead of as named module constants — two independently-maintained copies of the same formula, a real drift risk if one is tuned without the other. Water-filling allocation algorithm (`_allocate_weighted`) iteratively caps strategies at their `effective_cap` and redistributes the freed budget among remaining uncapped strategies until convergence — correctly handles cap-binding without needing an LP solver. Manual overrides are always respected over quality-weighted allocation, and disabled strategies are always zeroed, before any weighted redistribution runs.
- **Direct ORM use**: extensive — `select(StrategyGovernance)`, `select(CapitalAllocationPolicies)`, `select(StrategyControlState)`, `select(MetricsSummary).join(SimulationRuns)`, `session.get(StrategyConfigs, ...)`, raw `session.execute(text("SELECT pg_try_advisory_xact_lock..."))`, plus `session.flush()/commit()/rollback()` — no UnitOfWork/repository abstraction for governance, policy, or control-state reads in this file (some other reads/writes do go through injected repos like `AllocationOverridesRepository`/`AllocationRebalanceHistoryRepository`).

### src/autonomous_trading_platform/application/services/risk_budgeting_service.py (770 lines)
- Purpose: `RiskBudgetingService.compute()` produces advisory (not auto-applied) risk-budgeted portfolio weight recommendations across strategies — supporting equal-capital, inverse-volatility, fixed-risk-budget, and full Equal Risk Contribution (ERC) allocation modes — persisting a `RiskBudgetSnapshotRow` for observability.
- Notable: Explicitly documented as "backward compatible: does NOT modify QualityBasedReallocationService or existing AllocationOverrides. ### src/autonomous_trading_platform/application/services/strategy_health_lifecycle_service.py (1175 lines)
- Purpose: `StrategyHealthLifecycleService` — a 5-state (healthy/watch/degrading/critical/suspended) anti-flapping health state machine per strategy, driving an allocation-penalty scalar, separate from and never touching governance approval state. Auto-suspends after N consecutive CRITICAL cycles (operator-only recovery via `clear_suspension`).
- **Likely bug (verified in code, not just inferred)**: `_persist_state` always writes `evaluation_count=1` on the `StrategyHealthStateRow` (`src/.../strategy_health_lifecycle_service.py` around `_persist_state`), regardless of the strategy's true evaluation history. `_evaluate_strategy` reads this back as `evaluation_count = existing.evaluation_count if existing else 0` and passes it to `_apply_transition_rules`, which requires `evaluation_count >= config.min_observation_cycles` (default **3**, per `contracts/governance/strategy_health_lifecycle.py`) before the *first* escalation out of HEALTHY is permitted. Because the persisted value never advances past 1 across runs, a strategy whose metrics genuinely warrant escalation will have that escalation deferred by `_apply_transition_rules` (`"escalation deferred: observation_count=1 < min=3"`) **indefinitely** once `mode` is `alert`/`enforce` — the warm-up gate can never be satisfied under default config. This only manifests once lifecycle mode leaves the default `"observe"` (config default), so it may not have been caught by observe-mode-only testing/production use.
- **Duplication vs. `strategy_health_monitor.py`**: two independently-implemented health-classification state machines exist side by side. Both read the same `StrategyQualityScoreHistory`/`LivePerformanceMetricsService` inputs, both classify into the same `StrategyHealthStatus` enum, both upsert into the *same* `StrategyHealthStateRow` table via `StrategyHealthStateRepository.upsert`, and both call `AutoDemotionService` on critical health under enforce mode. `strategy_health_monitor.py` (this file's sibling, reviewed below) is materially simpler — no cooldown/anti-flapping, no auto-suspend, no allocation-penalty tiering. If both are wired into the runtime, they will race to overwrite the same health-state row for the same strategy with different verdicts; if only one is actually invoked, the other is dead code. Worth flagging for a follow-up "which one is live" check — not resolvable from static reading alone since both are fully-formed, production-quality services.
- Notable: `compute_target_status` is a clean pure function evaluated in strict severity order (CRITICAL → DEGRADING → WATCH → HEALTHY), each tier checking 6 independent signals (drawdown utilization, quality score, rolling Sharpe, win rate, consecutive quality decline, consecutive negative periods) — first match wins. Recovery is deliberately one severity step at a time (`_status_one_step_better`) even if metrics look fully healthy, and is blocked entirely during a post-transition cooldown window — escalation, by contrast, is never blocked by cooldown (safety bias). `SUSPENDED` is a hard floor requiring `clear_suspension` (operator action, always demotes to `WATCH` not `HEALTHY` — "conservative recovery").

- **`quality_based_reallocation_service.py`** — production-grade concurrency-safe idempotent rebalancing: `pg_try_advisory_xact_lock` + row-based fallback guard + rebalance-run-id idempotency, every guard path (including no-op skips) audit-logged.
- **`strategy_governance_service.py`** — the governance promotion gate is unusually rigorous: capital-bearing transitions (paper→live, research→paper) require an explicit `source_run_id` with no silent "latest run" fallback, and a misconfigured `PromotionRules` row (required fields left null) blocks promotion loudly (`PromotionCriteriaConfigurationError`) instead of silently promoting with no criteria enforced.
- **`strategy_health_lifecycle_service.py`** — the anti-flapping health-status FSM (cooldown windows, one-step-at-a-time recovery, escalation never blocked by cooldown, auto-suspend requiring operator clear) is a well-thought-out design — undermined by the `evaluation_count` persistence bug noted below.
- **`platform_backtest_service.py`** — checkpoint/resume with atomic tmp+rename writes, and an explicit fix-and-comment for a real historical bug (unseeded cash snapshot causing false drawdown-governance breaches) — good evidence of hardening from production incidents.

## Gaps/smells

1. **`shadow_runtime_validation_service.py`: `_hydrate_comparison_results` is a stub** — always returns 7 empty lists, so every `ShadowValidationSummary` from `finalize_shadow_run()` has empty per-dimension comparison detail regardless of what was actually persisted. Aggregate counts (`total_divergences`, `threshold_exceedances`, `divergence_by_category`) are still correct; only the detailed comparison-result hydration is missing.
2. **`strategy_health_lifecycle_service.py`: likely live bug** — `_persist_state` hardcodes `evaluation_count=1` on every write instead of incrementing from the existing row. `_apply_transition_rules` gates the *first* escalation out of HEALTHY on `evaluation_count >= config.min_observation_cycles` (default 3). Since the persisted counter never advances past 1, once lifecycle mode is `alert`/`enforce`, a strategy can become permanently stuck unable to escalate out of HEALTHY under default config. Currently latent because `HealthLifecycleConfig.mode` defaults to `"observe"` (no persistence), but a real bug the moment enforce/alert mode is turned on anywhere.
3. **Two parallel, overlapping strategy-health state machines**: `strategy_health_monitor.py` and `strategy_health_lifecycle_service.py` both classify the same strategies into the same `StrategyHealthStatus` values from overlapping inputs, both upsert the *same* `StrategyHealthStateRow` table, and both can trigger `AutoDemotionService`. If both are wired into the runtime they will race/overwrite each other's verdicts on the same row; if only one is live, the other is dead code carrying real audit/OTel side effects if ever invoked. Not resolvable by static reading — needs a wiring/DI-graph check (who actually calls each from the scheduler/cycle orchestrator).
4. **Three independently-maintained "quality"/"composite" scoring formulas** across this scope's files (`metric_lineage_service.py`, `quality_based_reallocation_service.py`, `strategy_catalog_service.py`'s `_composite_score`) — different weights, different purposes (blending vs. allocation vs. catalog sort), but similar enough in shape and naming that a maintainer tuning one could reasonably assume it affects the others. First two are confirmed literal duplicates (same weight constants); the third is a distinct formula but adds to the naming-confusion risk.
5. **CLAUDE.md's "never call ORM directly from services" claim is broadly false in this scope** — 17 of 37 files construct `select()`/`session.query()`/`session.add()`/`session.commit()` directly against ORM models with no repository/UnitOfWork abstraction (full list in "ORM-usage claim" section above). This is the dominant architectural pattern in `application/services/`, not an exception — worth escalating as a documentation-vs-reality mismatch rather than a bug in any one file.
6. **`runtime_snapshot_service.py`: silent section failures** — every `_capture_*` sub-method swallows all exceptions to `None`/`[]` with no logging, so a broken data source (e.g., Alpaca unreachable) produces a silently-empty snapshot section with no operator-visible signal that something failed vs. legitimately being empty.
7. **`platform_replay/runtime_hooks.py`** (read in a prior pass, re-confirmed relevant here): on trading-cycle exception, uses a raw `print(..., flush=True)` traceback dump alongside the structured failure result — bypasses the standard logger, a debug-era leftover.
8. **`portfolio_analytics_service.py`** (prior pass): `get_risk()` hardcodes `beta` and `average_pairwise_correlation` to `Decimal("0")` — if the API/UI presents these as computed risk metrics rather than placeholders, that's a user-facing honesty gap, not just an internal TODO.
